# Security Review (AD §6 threat model)

Reviewed against the implementation on 2026-10-21. Every mitigation points to code and, where possible, a test.

| Threat | Mitigation | Code | Test |
|---|---|---|---|
| Impersonation of a Mac or iPhone | Pairing binds Ed25519 identity keys to an X25519 exchange; the user compares the SAS; sessions need the per-pair PSK **and** an Ed25519 signature over fresh nonces | `PairingProtocol`, `SessionAuthenticator`, `NetworkParameters` | `PairingProtocolTests.tamperedKeyDetected`, `spoofedPeerID`, `SessionAuthenticatorTests.*` |
| Malicious Bonjour records | TXT data is display-only. The advertised peer ID must match the authenticated key after pairing | `BonjourBrowser`, `SenderService.pair` | code review |
| Man-in-the-middle during pairing | 6-digit SAS from HKDF over the full transcript; the responder signs the transcript; confirmation HMACs | `PairingCrypto`, `PairingProtocol` | `PairingCryptoTests`, `tamperedKeyDetected` |
| SAS brute force | 3 failures per peer, plus a global bucket, then a 60 s lockout; one pairing at a time; the pairing listener is only up while "Allow new pairings" is on | `PairingRateLimiter`, `ReceiverService.handlePairing` | `PairingProtocolTests.rateLimited` |
| Replay | Fresh 32-byte nonces in every HELLO, signed in SESSION_AUTH; TLS record protection; the transfer outcome ledger refuses to write a committed ID twice | `SessionAuthenticator`, `TransferOutcomeLedger` | `replayIsIdempotent`, `retrySameID` |
| Passive eavesdropping and key compromise | TLS 1.2 ECDHE-PSK ChaCha20-Poly1305 (forward secrecy); resumption and tickets disabled | `NetworkParameters` | `NetworkLoopbackTests` |
| Unauthorised peer sends a file | Unknown PSK identity fails TLS; untrusted peer ID fails SESSION_AUTH; offer source must equal the authenticated peer | `ServiceAdvertiser`, `SessionAuthenticator`, `TransferReceiver.validate` | `unknownIdentityRejected`, `untrusted`, `spoofedSource` |
| Path traversal and unsafe names | Sanitizer keeps only the last component, strips control characters and leading dots, NFC, 255-byte cap; the receiver rejects names that aren't already sanitized; exclusive rename; the final path is checked to be inside the folder | `FilenameSanitizer`, `TransferPolicy`, `FolderDestinationStore.commit` | `traversalRejected`, sanitizer tests |
| Oversized frames and memory exhaustion | Header length is checked against per-type caps before buffering; bounded inbox; one transfer per session; at most 8 pending handshakes | `FrameCodec`, `SessionChannel`, `ServiceAdvertiser` | `FrameCodecTests`, `chunkStream` |
| Disk exhaustion | Free space ≥ size + 64 MiB headroom before accept; 100 MiB cap; staging purged after 24 h | `TransferReceiver.validate`, `StagingArea.purge` | `diskFull`, `purge` |
| Tampered chunks | Strict sequence and offset; SHA-256 verified against both the offer and COMPLETE before commit | `TransferReceiver.receive` | `corruptedChunk` |
| Executable delivery | Denied UTTypes (apps, scripts, executables); `LSFileQuarantineEnabled` so Gatekeeper checks anything opened | `TransferPolicy.defaultDeniedTypes`, macOS Info.plist | `deniedType` |
| Secret leakage | Identity seed and PSKs in the Keychain (`AfterFirstUnlockThisDeviceOnly`, data-protection keychain); never logged; unpair deletes them | `KeychainSecretStore`, `PairSecretStore` | `PairingCryptoTests` (stores) |
| Sensitive logs | `Redaction.filename`, peer short IDs, `Scrubber` on export; analytics carry only buckets, durations and codes | `BridgeDiagnostics` | `DiagnosticsTests` |
| Least privilege | iOS: PhotosPicker (no library entitlement), no background modes. macOS: sandbox, user-selected folder, app-scoped bookmark, hardened runtime | entitlements, xcconfigs | review |
| Custom crypto | Only CryptoKit primitives (X25519, Ed25519, HKDF, HMAC, SHA-256) and the system TLS stack | — | — |

## Residual risks
- The pairing connection is plain TCP until the SAS is confirmed. Its security rests on users actually comparing codes (standard SAS assumption).
- The TLS 1.2 PSK identity (the iPhone peer ID) is visible on the wire. It is a public key fingerprint, not a secret.
- The outcome ledger lives in memory. After a Mac app restart, a lost COMMITTED for a completed transfer could lead to a retry being saved as "name 2". This needs a lost acknowledgement *and* a restart in between.

## Cross-platform (Android/Windows)

Reviewed on 2026-10-23 against `feature/cross-platform` (ADR-013, ADR-014, ADR-015, and the ADR-010 cipher-suite section). Status words follow AGENTS.md. `VERIFIED` means a test was executed on 2026-10-23: Swift package tests, Kotlin `:core:test` and `:app:*` on the `Pixel_7_Pro` emulator, .NET `SpatialBridge.Core.Tests` (583 passed) and `SpatialBridge.Platform.Windows.Tests` on macOS (67 passed, 8 `[WindowsFact]` skipped), and the loopback interop/perf runs. No Windows machine has run anything yet, so every Windows runtime behaviour is `IMPLEMENTED`, not `VERIFIED`.

### Session TLS

| Item | Mitigation | Code | Test | Status |
|---|---|---|---|---|
| BouncyCastle TLS config (Kotlin, .NET) | TLS 1.2 only; the single suite 0xCCAC on both client and server; no resumption (`getSessionToResume` null, no session IDs, no tickets); no `status_request` echo (`allowCertificateStatus`, multi-cert status and trusted-CA indication off), because BoringSSL rejects that echo for certificate-less suites; identity decoded as strict UTF-8 and only 32-byte keys returned; handshake failures map to E004. Renegotiation is left at BouncyCastle's default and isn't pinned explicitly. Kotlin registers no JCA provider (lightweight API only) | `core/net/PskTls.kt`, `SpatialBridge.Core/Tls/PskTls.cs` | Kotlin `PskTlsTest` (matching, wrong PSK, unknown identity); .NET `TlsLoopbackTests`; interop matrix swift↔jvm↔dotnet | `VERIFIED` for handshake/key behaviour. | Network.framework downgrade (finding, fixed) | Network.framework always also offers and accepts the plain-PSK suites 0x00A8/0x00A9/0x00AE/0x00AF (no ECDHE, no forward secrecy). Before the fix, a Swift server completed a session with a client that offered only plain-PSK suites, and a Swift client accepted 0x00A8. `NetworkParameters.validateNegotiatedTLS` now cancels any TLS connection with E004 at `.ready`, before `SESSION_AUTH` or application data, unless it negotiated TLS 1.2 + 0xCCAC | `NetworkParameters.swift` (`validateNegotiatedTLS`), `NWFrameTransport.open`, `sb-swift Net.swift` | `TLSCipherSuiteTests`: `validation`, `negotiatesCCAC`, `serverRefusesDowngrade`, `clientRefusesDowngrade` (4/4 passed) | `VERIFIED` |
| Pairing transcript binds HELLO wire bytes (ADR-014) | The transcript absorbs the exact HELLO payload bytes sent and received, not a re-encoding, so serializer differences can't split the SAS or keys | Swift `PairingCrypto.swift`/`PairingProtocol.swift`; Kotlin `crypto/Crypto.kt`, `session/PairingProtocol.kt`; .NET `Crypto/Crypto.cs` (`PairingTranscript`), `Pairing/PairingProtocol.cs` | `pairing.json` vectors (incl. android→windows with non-ASCII names) in all three; Swift `PairingCryptoTests` ADR-014 cases and `PairingProtocolTests` "unknown HELLO key or non-canonical key order" | `VERIFIED` (vectors on all three, non-canonical HELLO on Swift only) |
| Canonical-JSON risk | Residual. Every port must still emit canonical JSON (sorted keys, raw UTF-8, `/` unescaped, padded unwrapped base64, integer-millisecond dates, nil omitted) for older Apple builds that predate ADR-014 and re-encode, for vectors and diffs. A port that drifts (for example `System.Text.Json` escaping `+<>&`, or `android.util.Base64.DEFAULT` wrapping lines) would pair with new builds but not with old ones, and the failure shows up as an SAS mismatch, not a decode error | `json/CanonicalJson.kt`, `Messages/ControlMessageCoder.cs` | `canonical-json.json` and `control-messages.json` vectors in Kotlin and .NET | `VERIFIED` for the vector set. | PSK-registration race | The initiator finishes pairing when it holds PAIR_CONFIRM, which can be before the responder has stored the PSK. It fails closed: an early session gets E004 because no key exists for that identity, and a key is never accepted for the wrong peer. .NET `LookupPsk` waits up to 5 s for an in-flight pairing. Swift reports "Paired" only after the rebuilt session listener is ready and relies on the sender's reconnect. Kotlin `SenderService` retries E004 3× with backoff, then waits 30 s or for a kick. Kotlin `JvmReceiverHost` (CLI only) has no wait | `ReceiverService.cs` `LookupPsk`, `ReceiverService.swift` (re-key window), `SenderService.kt` reconnect | interop `send-after-pair` (swift→swift, swift→dotnet, jvm→swift, jvm→dotnet) | `VERIFIED` for those pairs. Residual: an availability risk, not confidentiality. A JVM receiver isn't in the matrix |

### Residual risks (cross-platform)
- **Downgrade coverage:** there is no Kotlin or .NET test that a plain-PSK-only peer is refused. Those ports configure 0xCCAC only, but the guarantee rests on the BouncyCastle configuration and on the Swift-side tests.
- **Swift test harness:** `sb-swift serve` drives the listeners directly, without `ReceiverService`, so it never purges staging (perf.py: stale file kept). The app path (`ReceiverService.start` → `StagingArea.purge`) is covered only by the function-level `purge` test, and no test checks that `start()` triggers it.
- **Windows:** every runtime item (DPAPI, MotW, Hidden, firewall rule, NTFS naming) stays unverified until the Windows CI job or a Windows machine runs the `[WindowsFact]` tests.
