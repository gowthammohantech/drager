# ADR-015: Content types, platform values and filenames across platforms

Status: Accepted

## Context
- `TransferOffer.contentType` is an Apple UTI. Android knows MIME types and Windows knows file extensions.
- `DevicePlatform` decodes only `iOS` and `macOS`, so a HELLO from any other platform fails to decode.
- The Mac checks policy only against the UTI. A script offered as `public.data` would be accepted.
- Windows filenames have constraints that Apple filenames don't: reserved names, `<>:"|?*`, and no trailing dots or spaces.

## Decision
- **Platforms:**
  - `DevicePlatform` becomes an open string value. Known values are `iOS`, `macOS`, `android` and `windows`.
  - Unknown values decode and round-trip unchanged.
  - UI copy names the peer's platform, or uses "computer"/"phone" when it is unknown.
- **The wire carries UTIs only.** There is no protocol change.
  - Android maps the file extension to a UTI first, then the MIME type, and falls back to `public.data`. It uses a table shared with the vectors.
  - Android never sends `dyn.*` UTIs.
- **Receiver policy applies to every sender:**
  - Deny if the UTI conforms to the denied set (as today).
  - **Also deny by the extension of the offered filename.** The Mac uses `UTType(filenameExtension:)` conformance. Windows uses an extension denylist covering Windows executables and scripts (`exe msi bat cmd com scr ps1 vbs js jse wsf lnk hta cpl msc reg jar appx msix`…) as well as the Apple denied set.
  - Windows uses a UTI catalog generated from the macOS UTType database. Like the Mac, it rejects UTIs it doesn't know, except `dyn.*` UTIs. The iPhone sends those for unknown extensions, and Windows accepts them as plain data. The extension denylist still applies to them.
  - The extension check also runs on the final Windows save name, so `x.exe.` cannot get through as `x.exe`.
- **Filenames:**
  - Senders offer names that already pass Swift's `FilenameSanitizer.isSafe`. The `sanitizer` vectors are the reference.
  - The Windows receiver validates with the same rule, then maps the name to a valid Windows save name: reserved names get a suffix, illegal characters become `_`, and trailing dots and spaces are trimmed.
  - The final name is reported in `COMMITTED.savedFilename`, as collision renaming already does.
  - Windows marks received files with Mark-of-the-Web (Zone.Identifier, ZoneId=3).

## Consequences
- Apple builds released before this change can't talk to Android or Windows peers, because they fail to decode the platform value. Users must update.
- Content-type policy no longer depends on the sender labelling files honestly.
