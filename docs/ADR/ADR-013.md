# ADR-013: Android sender and Windows receiver as native protocol ports

Status: Accepted

## Context
BRD §6 lists Android and Windows as out of scope. We are now extending Spatial Bridge to both. The shared Swift package depends on Network.framework, CryptoKit, Security and UniformTypeIdentifiers, which do not exist on either platform.

## Decision
- **Roles mirror the Apple apps.** Android is a sender, like the iPhone. Windows is a receiver, like the Mac. The supported pairs are iPhone or Android → Mac or Windows. Reverse transfer is still post-MVP (BR-08).
- **Native implementations of `docs/API/PROTOCOL.md`:**
  - Android: Kotlin with Jetpack Compose (`Apps/SpatialBridge-Android`). The protocol lives in a pure-JVM `core` module.
  - Windows: C# .NET 10 with WinUI 3 (`Apps/SpatialBridge-Windows`). The protocol lives in a cross-platform `SpatialBridge.Core` library.
- **Session TLS is unchanged:** TLS 1.2, suite `TLS_ECDHE_PSK_WITH_CHACHA20_POLY1305_SHA256` (0xCCAC), as in ADR-010. Neither stock Android TLS nor Windows SChannel offers PSK suites, so both ports use BouncyCastle's TLS stack (`bctls-jdk18on`, `BouncyCastle.Cryptography`). Android uses the lightweight BC API and registers no JCA provider.
- **Conformance:** `Conformance/vectors` holds golden vectors generated from the Swift implementation, and `Scripts/interop.sh` runs a loopback interop matrix. Both are the compatibility gate (`docs/API/CONFORMANCE.md`).
- **Discovery:** Android and Windows rely on infrastructure Wi-Fi mDNS. They have no AWDL peer-to-peer.

## Consequences
- There are now three implementations of one protocol. Any protocol change must update the vectors first.
- Windows feature parity is best effort for the overlay, as ADR-008 already allows.
- WinUI 3 can be built only on Windows, so a Windows CI runner gates it.
